# 线路不降智率实施计划

**Goal:** 将线路详情的疑似降智轮次比例替换为 `(用量请求数 - 降智请求数) / 用量请求数`。

**Architecture:** 复用后台账号质量监控的明确判定，按规则绑定的被测分组保存账号状态事件。转发记录实际尝试开始时间，用量入库时按该时刻查找状态并固化快照。线路走势只聚合原生用量记录；不把当前状态套用到历史请求。

**Tech Stack:** Go、PostgreSQL、Vue、Vitest。

## 已确认口径

- 按账号和用量所属分组统计，不将某次检测错误直接推断为每条回答错误。
- 明确判错标记降智，明确通过恢复；超时、报错和判题不确定不改变既有标记。
- 多模型检测任一明确判错标记整个账号；只有配置样本全部明确通过才恢复。
- 未有明确检测结论的请求没有降智标记，按公式计入不降智；提示说明这一限制。
- 原生用量记录的普通查询口径作为分母，未知用量排除，重试产生独立用量行时保留原生用量计数，不额外拼接错误日志。
- 旧用量缺少请求时状态快照，显示暂无数据，不能回填为正常；混合桶注明快照缺失。
- 无请求显示暂无数据，不绘制虚假的 0% 或 100%。
- 本次只本地实现和验证，不合并 main、不推送、不部署。

## 实施步骤

- [x] 检测状态：先测试明确错误、恢复、超时不覆盖标记，再接入现有受租约保护的质量结果事务。
- [x] 用量快照：保存转发尝试开始时间；数据库迁移增加不可追溯填充的状态快照，通过带索引的状态事件查询固化请求当时结论。
- [x] 统计查询：单独聚合分组用量、降智请求及已有快照数量，不改变成功率、缓存和首字口径。
- [x] 前端：先写 95%、100%、无请求、旧数据及混合快照测试，再替换指标名称、曲线和明细。
- [x] 验证：运行直接相关 Go/Vitest 测试、类型检查和隔离 PostgreSQL 集成测试；检查桌面及窄屏图表。

## 关键验证

- 降智期间开始、恢复后完成的请求仍为降智；降智前开始的长请求不被追溯标记。
- 账号恢复不改变已写入用量；分组隔离、多规则状态和请求边界正确。
- 未判定结果、旧数据、重复用量写入和跨账号重试不虚构结果。
