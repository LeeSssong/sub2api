# 轻量运行时文件更新设计

## 1. 背景与当前行为

当前发布规则要求验收站、主站及附属服务的所有部署都从已推送、干净且与 `origin/main` 完全一致的根 `main` 发起，并通过既有镜像或蓝绿发布链生效。该门禁适合后端、数据库迁移、容器镜像和需要构建的前端，但对于服务器已经直接读取、覆盖后无需重启即可生效的少量静态文件，完整发布链成本过高。

仓库现状同时表明，“前端文件”不能直接作为轻量更新资格：Sub2API Vue 前端、独立测试站前端和首页资源通常在构建阶段进入镜像或二进制。只有通过运行拓扑和目标路径证明确实由活动服务直接读取的文件，才可能采用本设计。

## 2. 目标

- 为无需构建、重启、reload、迁移或流量切换的运行时直读文件提供主站轻量更新路径。
- 保留根 `main`、`origin/main` 和 Git commit/tree 作为唯一代码来源。
- 通过备份、校验和、原子替换、即时验证和自动回滚保持可追溯性与可恢复性。
- 明确记录仓库版本、主站运行态和验收站运行态之间的临时差异。

## 3. 非目标

- 不允许直接修改服务器文件后再反向补提交。
- 不允许从功能 worktree、候选分支、本地未提交内容、服务器现有文件、容器文件或 Docker volume 取源。
- 不为普通 Vue、TypeScript、Go 或其他源码取消构建和完整发布要求。
- 不允许借轻量更新绕过主站明确授权、最小验证、凭据保护或线上验证。
- 本设计不直接实现自动化热更新脚本；首次执行前仍需根据实际目标路径确认安全命令和权限边界。

## 4. 方案比较

### 方案 A：受控的运行时直读文件例外（采用）

按运行行为而非扩展名或目录名判定资格。只有能证明活动服务直接读取目标文件，并且替换无需构建、重启、reload、迁移或流量切换时，才允许使用轻量路径。

优点是范围可证、风险可控，且不会错误放行被打包进镜像或二进制的前端源码。代价是每次首次覆盖某类文件前都必须核实运行拓扑和目标路径。

### 方案 B：所有前端或静态文件均可直接覆盖（不采用）

按“前端”“静态资源”或文件扩展名放行。流程最短，但无法区分宿主直读文件、镜像内文件、构建输入和带哈希的前端制品，容易造成覆盖无效、缓存错配或运行态不可复现。

### 方案 C：所有改动继续走完整发布链（不采用）

维持当前规则。可追溯性最强，但不能满足用户降低简单、即时生效文件更新成本的目标。

## 5. 授权与资格合同

新增第四类主站明确授权语义：`轻量更新主站`。普通“更新”“覆盖一下”“上线”“继续”不构成该授权。

一次轻量更新必须同时满足以下条件：

1. 改动已经提交并推送到根 `main`。
2. 根目录当前分支为 `main`、非 detached HEAD、工作树干净，且 `HEAD` commit/tree 与 `origin/main` 完全一致。
3. 源文件完全来自该根 `main`，目标文件与仓库文件的映射明确。
4. 有证据证明活动服务从宿主或只读挂载目录直接读取目标文件，替换后无需编译、构建镜像、重启进程或容器、reload 配置、执行迁移或切换流量。
5. 改动不涉及后端可执行代码、接口契约、数据库、迁移、配置、环境变量、密钥、证书、鉴权、安全策略、计费写入、任务调度或容器内置文件。
6. 已完成与改动直接相关的最小本地验证，且可以定义覆盖后的线上专项验证。

任何条件无法证明时必须 fail closed，退回常规或快速完整发布路径。文件名、扩展名、所在目录或“前端改动”的口头描述均不能单独证明资格。

## 6. 执行流程

1. 记录目标环境、用户授权、源 commit/tree、仓库源路径、服务器绝对目标路径及资格证据。
2. 读取并记录覆盖前目标文件 SHA256；将原文件备份到同文件系统的受控备份位置。
3. 将来自根 `main` 的源文件传输到目标目录中的临时文件，校验临时文件 SHA256 与本地源文件一致。
4. 保留原属主、属组和权限，使用同文件系统内的原子 `rename` 或等价操作替换目标文件；不得直接流式写入活动目标文件。
5. 重新读取活动目标文件 SHA256，确认与源文件一致。
6. 执行改动对应的页面、资源或内容专项验证，并确认现有健康入口仍正常。
7. 验证失败或结果不确定时，使用同样的原子替换方式恢复备份，并再次执行专项验证。
8. 记录最终状态、覆盖前后 SHA256、备份位置、验证结果、是否回滚，以及主站和验收站运行态差异。

同一次轻量更新只覆盖本次授权和记录中的明确文件。不得在执行时顺带增加其他文件。

## 7. 双站与版本语义

轻量更新不要求同步验收站，也不将验收站人工验收作为前置条件。执行后必须明确记录：

- 仓库、主站和验收站可以具有相同 source commit/tree；
- 主站存在基于该 commit/tree 的已记录轻量文件覆盖；
- 验收站未应用该覆盖，除非另有独立记录；
- 因此不得仅凭 commit/tree 声称主站与验收站运行内容完全一致。

下一次完整发布若从包含该文件改动的 `main` 构建并成功生效，应清除对应运行态差异记录。若完整发布不包含该改动，则差异继续存在并必须继续提示。

## 8. 失败与安全语义

- 找不到直接读取证据、目标是符号链接、目标路径漂移、权限无法安全保留、校验和不一致或无法执行原子替换时，停止并退回完整发布路径。
- 目标位于容器可写层、Docker volume、数据库数据目录、上传目录或凭据目录时，不得使用轻量路径。
- 需要 Caddy、Nginx 或应用 reload 才生效的配置不属于本路径，即使 reload 不导致明显停机。
- CDN、浏览器或代理缓存可能导致旧内容继续可见时，必须把缓存验证纳入专项验证；不得仅凭服务器文件校验宣称用户侧已生效。
- 轻量更新失败不触发数据库或镜像回滚，只恢复本次明确覆盖的文件；无法确认恢复成功时停止后续发布并通知用户。

## 9. 规则文件改动

用户批准本规格后，同步修改：

- `AGENTS.md`：在发布与环境硬门禁中增加受控轻量更新例外和第四种主站授权。
- `docs/project/acceptance-station-global-constraints.md`：增加第四条授权路径、执行步骤、双站差异语义和检查清单。
- `docs/project/native-sub-incremental-delivery-constraints.md`：更新授权摘要，并在根线程快速发布协议中增加轻量运行时文件更新例外。

本轮不修改部署脚本、服务器文件、任务队列或项目总账。

## 10. 验证策略

- 使用文本检索确认三份规则中的主站授权数量、授权短语和例外条件一致。
- 检查所有原有“仅三种授权”“所有部署必须走完整发布链”等绝对表述均已正确收窄，不留下相互矛盾的规则。
- 检查规则仍明确禁止从未推送内容、候选分支、服务器文件、容器文件和 Docker volume 取源。
- 检查未把普通前端源码或静态资源默认归入轻量路径。

## 11. 发布与回滚

本轮交付仅修改制度文档，无服务器发布、重启、配置 reload、迁移或运行态变化。文档改动通过 Git revert 回滚。

后续实际轻量更新的回滚按第 6 节恢复单文件备份；若不满足该回滚条件，则不得采用轻量路径。
